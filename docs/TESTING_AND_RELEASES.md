# Проверки, сборка и публикация

## Выбор проверок

Сначала воспроизведи проблему на синтетических данных. Добавляй регрессионный тест для реального риска, а не копию реализации. Для изменений движка проверяй сохранность файла и ошибочные пути; для обратимой локальной правки текста не создавай искусственный unit test.

Критические сценарии:

| Область | Проверка результата |
| --- | --- |
| Переименование | Байты, размер, точные mtime/birthtime, inode на поддерживаемой ФС; расширение; undo и перезапуск |
| Конфликты | Существующее назначение не затронуто; обмен имён; дубликат назначения; регистр/Unicode; недопустимое имя |
| Ошибка/прерывание | Откат/журнал; нельзя заявлять полное восстановление, если оно не удалось |
| Импорт/порядок | Файлы+папки, повторные пути, ссылки, вложенность; естественная сортировка; вставка вверх/вниз и по краям |
| Метаданные | EXIF и его отсутствие; дата съёмки; инспектор readonly; смена выбранного файла |
| Дубликаты | Равные байты, одинаковый размер при разных байтах, пустые файлы, ссылки, отмена, изменение во время чтения |
| Удаление дубликатов | Несколько групп, смена keeper, ошибочная отметка keeper, all-copies без ручного выбора, отмена подтверждения |
| OCR | RU/EN без EXIF, изображение без текста, повреждённый файл, фильтры/пороги/фраза, кэш и изменение исходника |
| Действия OCR | Текущий фильтр/снимок подтверждения, скрытые отметки, stale-файл, коллизия экспорта, копия сохраняет исходник, частичный успех |
| Внешние диски | Только реально проверенные ФС/права; сохранение дат, поддержка rename/Корзины, отключение диска |

Не удаляй реальные пользовательские файлы для проверки. Генераторы создают новые синтетические папки и отказываются перезаписывать существующие: `--make-fixtures PATH`, `--make-duplicate-fixtures PATH`, `--make-text-fixtures PATH`. Для теста удаления допустим подготовленный синтетический файл; не очищай Корзину.

## Сборка DMG

1. Проверь git status и согласованность checkout. Не собирай установщик из файлов, которые параллельно редактирует другой чат.
2. При новой выпускаемой сборке синхронно обнови CFBundleShortVersionString и CFBundleVersion в Info.plist, Installation.txt, README RU/EN и CHANGELOG.md. Сейчас принят формат 1.0.x / build x; следующую версию определяй по актуальному состоянию, а не по этому документу.
3. Запусти `zsh build.sh` из корня. Нужны macOS, Swift CLT, codesign, hdiutil; скрипт собирает arm64 для macOS 26.
4. Скрипт запускает полный `--self-test` с GRAPE_TEST_LANGUAGE=en и ru, проверяет ad-hoc подпись, создаёт приложение/ZIP/DMG и SHA256SUMS.txt в dist/. Любой провал разбирается до передачи DMG.
5. Проверь затронутое поведение в реально запущенном приложении по INTERFACE_RULES.md. Тестовая копия может использовать отдельный bundle ID и GrapeTestStorage/GrapeTestFiles; пользовательские данные не затрагиваются.
6. Проверь DMG через hdiutil verify, смонтируй read-only, проверь codesign --verify --deep --strict для приложения внутри, версию/build и отсутствие GrapeTest* в release Info.plist. Отмонтируй образ после проверки.
7. Сравни SHA-256 окончательного DMG с SHA256SUMS.txt. Именно этот файл передавай пользователю и загружай в релиз, без повторной упаковки после проверки.

Не делай вывод о повреждении release-подписи только по копии .app в синхронизируемой папке: Finder/iCloud могут добавлять xattrs. Проверяй приложение в готовом DMG или чистой временной копии. Не удаляй quarantine и не отключай Gatekeeper на компьютере пользователя ради теста установки.

## GitHub

Публикация выполняется по запросу пользователя. Обычный commit/push не равен созданию релиза. Перед публикацией:

1. Убедись, что версия и код закоммичены, отправлены в нужную ветку и тег указывает на проверенный коммит. Не включай личные файлы, состояние тестов, кэш, ключи и артефакты .app/.dmg в Git-историю; DMG — release asset.
2. Проверь существование версии релиза, чтобы не создать дубль или не заменить чужую публикацию. Описание RU/EN охватывает финальное поведение, ограничения, установку и обратную связь; если публичная версия пропущена, включи её значимые изменения в следующий релиз.
3. Для gh передавай длинный текст через --notes-file/--body-file. Не встраивай Markdown и пользовательский текст в исполняемый shell-код. Не сохраняй токены в исходниках или выводе.
4. Загрузи проверенный DMG и SHA256SUMS.txt сначала в draft. Проверь версию, target commit, размеры и digest assets, затем опубликуй и обозначь Latest при необходимости.
5. Проверь публичное скачивание без авторизации и SHA-256 скачанного файла. Проверь публичный URL, тег и статус релиза; только после этого сообщай об успешной публикации.
6. При правках одного описания сохраняй остальной текст и не переупаковывай DMG. Тег уже опубликованной версии не переназначай молча.

## Подпись и первый запуск

Сейчас используется ad-hoc подпись, без Developer ID и нотариального заверения Apple. Она не обеспечивает обычный беспрепятственный запуск скачанного приложения. README RU/EN и релиз содержат объяснение Gatekeeper и официальную инструкцию разрешения конкретного приложения через «Системные настройки → Конфиденциальность и безопасность → Всё равно открыть».

Не обещай, что открытый код/совпадение SHA-256 доказывает отсутствие вредоносного ПО. Не называй предупреждение Apple ложным обнаружением вируса. Для полноценной подписи и нотариального заверения требуется участие владельца Apple Developer Program; не запрашивай пароль или секреты в чате и не обещай обход одним изменением DMG.

## Итог задачи

Сообщи версию, реальные выполненные проверки, расположение/ссылку на результат и непроверенные существенные ограничения. Если нового релиза нет, не представляй локальный DMG как опубликованный. Не повторяй полный тестовый цикл без новых изменений/рисков после успешной проверки.
